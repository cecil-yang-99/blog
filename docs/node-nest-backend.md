## Node.js / NestJS 后端常见问题总结

这篇记录后端开发中经常遇到的 Node.js 与 NestJS 问题。重点不是背概念，而是理解问题为什么发生、应该从哪一层定位，以及工程里更稳妥的处理方式。

## 1. Node.js 为什么适合 I/O 密集型服务？

**总结**

Node.js 使用事件循环和非阻塞 I/O，把等待网络、数据库、文件系统响应的时间让出来，因此适合 API 网关、BFF、实时服务、任务编排等 I/O 密集型场景。

**分析**

Node.js 的主线程负责执行 JavaScript 和调度回调，真正的异步 I/O 由底层能力处理。对于大量请求来说，只要业务逻辑不是长时间占用 CPU，主线程就可以持续接收请求并分发异步任务。

但这并不代表 Node.js 天然适合所有场景。CPU 密集型任务，例如大文件压缩、复杂加密、图片处理、海量 JSON 解析，会长时间阻塞事件循环。遇到这类任务应该考虑 worker_threads、独立任务服务、队列或交给更适合的运行时处理。

## 2. 什么是事件循环阻塞，如何排查？

**总结**

事件循环阻塞指主线程长时间执行同步代码，导致请求响应、定时器、异步回调都被延迟。

**分析**

常见原因包括同步文件读写、大对象 JSON.stringify、复杂正则、循环计算、一次性处理过大的数组。表面现象通常是接口偶发超时、CPU 升高、日志时间间隔异常、健康检查变慢。

排查时可以先看接口耗时和 CPU，再加 event loop delay 指标。修复方向是把大任务拆小、改成流式处理、使用异步 API、限制单次处理数据量，或者把 CPU 任务移出主线程。

## 3. NestJS 的 Module、Provider、Controller 分别解决什么问题？

**总结**

Controller 负责接收请求，Provider 承载业务能力，Module 负责组织依赖边界。

**分析**

NestJS 的核心价值是把后端代码从“到处 import 和 new”变成由依赖注入容器管理。Controller 不应该写大量业务逻辑，而应该把请求参数转换成服务层能理解的输入。Provider 通常是 service、repository、client、adapter 等可复用能力。Module 则定义这些能力在什么范围内可见。

一个清晰的模块边界可以减少循环依赖，也方便测试。比如订单模块需要用户信息时，可以依赖 UserModule 导出的 UserService，而不是直接跨目录访问内部实现。

## 4. NestJS 依赖注入失败通常是什么原因？

**总结**

最常见原因是 Provider 没有注册、Module 没有 import、Provider 没有 export，或者出现了循环依赖。

**分析**

错误信息里经常会出现 “Nest can't resolve dependencies”。定位时先看报错的类和第几个构造参数，再检查这个参数对应的 provider 是否在当前 module 的 providers 中，或者是否来自已 import 的 module。

如果 provider 定义在另一个 module 中，那个 module 需要在 exports 中导出它，当前 module 还要 imports 那个 module。循环依赖可以用 forwardRef 临时解决，但更好的方式通常是重新划分模块职责，抽出共享能力或通过事件解耦。

## 5. Middleware、Guard、Interceptor、Pipe、Filter 的区别是什么？

**总结**

Middleware 处理原始请求，Guard 判断能不能访问，Pipe 校验和转换输入，Interceptor 包裹请求前后逻辑，Filter 统一处理异常响应。

**分析**

这些机制容易混用，但职责不同。鉴权授权更适合 Guard，因为它决定请求是否继续。DTO 校验和类型转换适合 Pipe。日志、响应包装、超时、缓存、链路追踪适合 Interceptor。异常格式标准化适合 Exception Filter。

保持职责清楚很重要。比如不要在 Pipe 里查权限，也不要在 Controller 里手写统一错误格式。框架提供这些层，是为了让横切逻辑可复用、可测试、可组合。

## 6. REST API 应该如何设计错误响应？

**总结**

错误响应应该稳定、可读、可被前端或调用方识别，不能只返回一段随意的 message。

**分析**

一个实用的错误结构通常包含 code、message、details、requestId。HTTP 状态码表达大类，例如 400 表示请求错误，401 表示未登录，403 表示无权限，404 表示资源不存在，409 表示状态冲突，500 表示服务内部错误。

业务错误不要滥用 500。比如余额不足、订单状态不允许取消、资源已存在，都应该是可预期错误。稳定的错误 code 能让前端做明确提示，也方便日志检索和告警聚合。

## 7. 数据库事务应该放在哪一层处理？

**总结**

事务应该包住一个完整业务动作，而不是零散地放在 repository 的每个小方法里。

**分析**

比如“创建订单并扣减库存”是一个业务动作，这两个写操作必须一起成功或一起失败。事务边界通常适合放在 application service 或 use case 层，由它协调多个 repository。

如果每个 repository 方法自己开事务，多个方法组合时就很难保证一致性。对于 NestJS 项目，可以通过 ORM 的 transaction API、Unit of Work、request scoped context 或显式传递 transaction manager 来保证同一个业务流程共享事务。

## 8. 为什么要使用 DTO 和 ValidationPipe？

**总结**

DTO 定义接口输入形状，ValidationPipe 负责运行时校验和转换，避免脏数据进入业务层。

**分析**

TypeScript 类型只在编译期存在，运行时请求体仍然可能是任意结构。没有校验时，业务层会被迫处理大量 undefined、错误类型和非法值，问题也更晚暴露。

DTO 应该描述外部输入，不要直接复用数据库实体。数据库实体常包含内部字段和关系结构，直接暴露给接口会让 API 合同和存储模型强耦合，也容易引入越权字段写入问题。

## 9. Node.js 服务如何处理高并发下的限流和超时？

**总结**

高并发保护要同时考虑入口限流、下游超时、重试策略和资源隔离。

**分析**

限流可以保护服务不被瞬时流量打穿，常见策略有固定窗口、滑动窗口、令牌桶。超时可以避免请求无限等待下游服务。重试必须谨慎，最好只对幂等请求重试，并设置退避策略，否则可能放大故障。

数据库连接池、HTTP client 连接池、队列并发数也需要限制。很多线上故障不是代码逻辑错，而是没有边界：请求一直堆积，连接耗尽，最终整个服务不可用。

## 10. NestJS 项目应该如何组织日志和可观测性？

**总结**

日志、指标和追踪要围绕一次请求或一个任务串起来，核心目标是快速回答“哪里慢、哪里错、影响多大”。

**分析**

基础日志至少包含 requestId、method、path、status、duration、userId 或 tenantId 等上下文。业务关键节点应该记录结构化日志，避免只输出自然语言字符串。

指标适合观察趋势，例如请求量、错误率、延迟分位数、队列积压、数据库耗时。分布式追踪适合定位跨服务调用链。对于 NestJS，可以通过 Interceptor 注入请求日志和耗时统计，通过 Exception Filter 统一记录异常，通过中间件或上下文存储传递 requestId。

## 总结

Node.js 后端的核心风险通常集中在三类：事件循环被阻塞、依赖和模块边界混乱、外部资源没有保护。NestJS 提供了 Module、DI、Guard、Pipe、Interceptor、Filter 等结构化工具，但这些工具只有在职责清楚时才真正有价值。

写后端服务时可以反复检查几个问题：

1. 这个逻辑是否会阻塞事件循环？
2. 这个模块边界是否清晰？
3. 输入有没有在进入业务层前完成校验？
4. 错误响应是否稳定可识别？
5. 下游依赖是否有超时、限流和观测？

把这些问题处理好，服务的稳定性和可维护性会比单纯堆功能强很多。
